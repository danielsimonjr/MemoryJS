# Performance, stability, and security review — 2026-09-12

Reviewed from `364b94b` on `master`. This change addresses reproduced defects
in persistence, HTTP input handling, authorization, and fuzzy search. It also
adds focused benchmarks and regression coverage. No dependency versions change.

## Findings and fixes

| Area | Evidence and impact | Change |
| --- | --- | --- |
| Disk search tiers | Twenty simultaneous first-use inserts retained only one entry in both `DiskWarmTier` and `BrotliColdTier`, in memory and after reopening. Separate loads and whole-file flushes raced. | Serialize reads, writes, deletion, clear, and reload per instance across all keys. Failed deletion preserves insertion order. Readers cannot observe a failed write's temporary state. |
| API-key authorization | Mutating `issue().record.scopes` granted an additional scope. An invalid `expiresAt` authenticated indefinitely. Other accessors and loaded arrays also shared authorization state. | Copy authorization records/scopes at boundaries; validate expiry/TTL and restored records; reject duplicate IDs/hashes; validate a replacement before publishing either lookup index. |
| REST adapter | JSON bodies were buffered without a size cap or prior authentication. Malformed URL escapes rejected `dispatch`; internal exception messages were returned to clients. | Authenticate before body reading; configurable `maxBodyBytes` defaults to 1 MiB; enforce declared and streamed byte limits; return 400/413 for malformed/oversized input; mask 5xx messages and validate error statuses. |
| File writes | Several persistence paths ignored `bytesWritten`, although a low-level write can complete partially. | The shared durable writer loops until all bytes are written and rejects zero progress. Graph append and segment staging use `FileHandle.writeFile`. UTF-8 partial-write and failure tests verify complete output and original-file preservation. |
| Policy evaluation | Each condition flattened the entire context again, then all matching rules were sorted. Shared object references could hide a valid resource attribute; inherited object properties could appear present. | Flatten lazily once per evaluation; select the highest-priority decision in one pass with deny precedence; use a prototype-free attribute map and ancestor-only cycle tracking. |
| Fuzzy search | The main-thread matcher computed a full distance despite having a cutoff. Workers skipped entity types and individual words in observations. Comma-joined tag cache keys collided and sorting mutated callers' arrays. | Share a banded, cutoff-aware Levenshtein implementation; retain exact two-argument behavior; align worker field matching; encode copied tag arrays and invalidate cache when replacing the n-gram index. |
| Native SQLite startup | Requiring `better-sqlite3` loads only its JavaScript wrapper, so the installation probe could incorrectly report success. | Open an in-memory database, execute a query, and close it before reporting success, including after a rebuild. |
| Test portability | The baseline suite's SQLite lazy-load test failed because the tsx CLI opens an IPC listener unavailable in this environment. | Use Node's tsx import hook directly and clean up the temporary database. The native lazy-load assertion remains intact. |

## Measured performance

Node v24.19.0, Linux, same container. Median of seven warmed samples per case;
baseline and changed versions ran sequentially. Both produced the same decision
checksum. These are CPU microbenchmarks, not end-to-end service throughput.

| Workload | Iterations/sample | Before | After | Ratio |
| --- | ---: | ---: | ---: | ---: |
| Policy: 100 rules × 4 conditions, 100 subject attributes | 200 | 1,284.859 ms | 4.102 ms | 313× |
| Fuzzy near match: 512 UTF-16 units, edit cutoff 5 | 300 | 388.640 ms | 6.988 ms | 56× |
| Fuzzy non-match: 512 UTF-16 units, edit cutoff 5 | 300 | 566.325 ms | 1.056 ms | 536× |

Run `node --import tsx benchmarks/review-bench.ts [repo-root]` against each
revision to reproduce the workloads. Improvements depend on rule count, string
length, and cutoff; these ratios should not be generalized to every query.

## Validation

- Full default suite: **8,097 tests passed across 348 files**, without suppressing
  unhandled errors. Final focused validation: **149 passed**, including one
  additional fuzzy-cache regression added after the full run.
- Independent full-matrix oracle checks bounded and exact Levenshtein results
  for all pairs in a small exhaustive corpus, including Unicode cases.
- Concurrent cold-start writes, overlapping clear/reload operations, injected
  persistence failure, mutable authorization snapshots, malformed HTTP input,
  native-addon lazy failure, and partial file writes have regression tests.
- Type checking, lint, ESM/CJS build, declaration generation, and export checks pass.
- Root and all four tool-package dependency audits returned no known vulnerabilities.

## Compatibility and limits

- HTTP consumers sending JSON larger than 1 MiB must explicitly set
  `maxBodyBytes`. Invalid JSON now returns 400; server errors expose a generic
  message while details remain in server logs. Framework adapters calling
  `dispatch` directly must enforce their own transport body limit.
- Key records returned by the store are snapshots. Invalid or duplicate
  persisted credentials now reject loading rather than silently authenticating.
- Disk-tier locks coordinate one instance in one process. Multiple instances or
  processes sharing one shard still require external coordination. Tier eviction
  callbacks retain their existing asynchronous, best-effort semantics; this
  change does not make cross-tier demotion crash-atomic.
- Validation used Linux/Node 24 and native SQLite. No live PostgreSQL server or
  real HTTP listener was available; HTTP tests use real request streams. The
  repository's CI matrix covers Node 22/24 on Linux, Windows, and macOS.

The persistence changes follow the documented distinction between individual
[`FileHandle.write` calls and complete-file writes](https://nodejs.org/api/fs.html).
The HTTP limits and error handling follow
[Node's security guidance](https://nodejs.org/en/learn/getting-started/security-best-practices).
The native probe exercises the documented
[`better-sqlite3` database constructor](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md).
