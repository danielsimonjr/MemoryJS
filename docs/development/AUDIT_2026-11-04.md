**Status:** Planning document. Nothing below is applied yet. Every finding was verified against source at `HEAD = 8e9f88b` (v4.4.0 + Unreleased RefIndex fix) with `file:line` evidence; call-site greps were run for every "unwired follow-up" before it was listed.

## 1. Executive summary

The codebase is in good shape: the 2026-07 `OPTIMIZATION_OPPORTUNITIES.md` programme (S1–S10, Sec1–Sec10) landed, delta persistence is the norm in `EntityManager` / `RelationManager` / `ObservationManager`, and typecheck + lint pass. What remains falls into three buckets:

1. **Residual O(graph) work on hot paths.** A handful of per-call allocations and full-graph rewrites survived the delta-persistence migration: `createEntities` and `createRelations` still build a `Set` of every entity name per call; `SearchFilterChain` rebuilds a `Map` of the whole graph on every search to resolve draft→published visibility even when no drafts exist; `SQLiteStorage` runs two `CREATE TABLE IF NOT EXISTS` DDL statements on **every** embedding read/write; BM25 recomputes IDF inside the per-document loop; several managers (`HierarchyManager.setEntityParent`, `GovernanceManager`, `AgentMemoryManager.addWorkingMemory`, `ArtifactManager` retry, `DecayEngine` forget) still deep-copy and rewrite the whole graph for a single-entity change.
2. **Infrastructure that is built but not reachable.** `BloomPreScreener` is implemented in `FuzzySearch` but nothing constructs or attaches one; `SQLiteStorage.recordFilter` (the `PartialIndexAdvisor` entry point) has zero callers so `MEMORY_SQLITE_AUTO_INDEX` is effectively dead; `MaterializedViews` still uses coarse invalidation; `SQLiteBackend.preserveCallerIds` throws citing a `renameEntity` primitive that has existed since v2.x; and ~12 `@public`-tagged modules (`ObservationStore`, `MaterializedViewsManager`, `CompressedMap`, `CachePressureCoordinator`, `IndexHealthMonitor`, …) are returned by public `ManagerContext` getters but exported from no barrel, so consumers cannot name their types.
3. **Documentation drift.** `CLAUDE.md` lists four modules that were deleted (`SynonymManager`, `BackgroundIndexer`, `PartitionedInvertedIndex`, `SearchStream`) and an env var (`MEMORY_SYNONYM_EXPANSION`) for one of them; README documents `MEMORY_RBAC_ENABLED` and `MEMORY_DEFAULT_PROJECT_ID`, neither of which is read anywhere in `src/`; `MEMORY_LLM_QUERY_PLANNER_PROVIDER` is documented in two places and read nowhere; two env vars that *are* read (`MEMORY_AUTO_LINK`, `MEMORY_OBSERVATION_DEDUP`) are undocumented; the Tools table lists 4 of 7 tools; `docs/architecture/API.md` misses ~10 `ManagerContext` getters.

**Totals:** 15 optimization items (12 implementable, 3 deferred), 9 completion items (6 implementable, 3 deferred-or-partial), 9 docs items (8 implementable, 1 deferred). **22 implementable items** grouped into 6 parallel batches in §7.

### 3.2 Detail

#### OPT-1 — `ensureEmbeddingsTable()` runs DDL on every embedding operation
- **Evidence:** `SQLiteStorage.ensureEmbeddingsTable` (`src/core/SQLiteStorage.ts:2417-2432`) executes `CREATE TABLE IF NOT EXISTS embeddings …` **and** `CREATE INDEX IF NOT EXISTS idx_embedding_model …` via `db.exec`. It is called at the top of `storeEmbedding` (`:2448`), `getEmbedding` (`:2471`), `loadAllEmbeddings` (`:2495`), `loadEmbeddingMetadata` (`:2518`), `removeEmbedding` (`:2536`), `clearAllEmbeddings` (`:2551`), `hasEmbedding` (`:2568`), `getEmbeddingStats` (`:2588`). Each of those also calls `this.db.prepare(...)` fresh (`:2453, 2473, 2497, 2520, 2537, 2569, 2590-2591`) despite `prepareCached` existing (`:346`). `SQLiteVectorStore.add` → `storeEmbedding` is called once per entity during `SemanticSearch.indexAll` (`src/search/VectorStore.ts:273`), and `MemoryEngine.addTurn` (`src/agent/MemoryEngine.ts:306`) hits it per turn.
- **Change:** add `private embeddingsTableReady = false;` next to `stmtCaches`. In `ensureEmbeddingsTable`: `if (this.embeddingsTableReady) return;` … run the two `exec`s … `this.embeddingsTableReady = true;`. Reset the flag to `false` in `clearCache()` (`:1875`) and `close()` (`:2210`) right where `this.db = null`. Replace `this.db.prepare(` with `this.prepareCached(this.db, ` in `storeEmbedding`, `getEmbedding`, `removeEmbedding`, `hasEmbedding` (the per-entity ones; leave the bulk/stats ones). `prepareCached` is keyed per connection via a `WeakMap`, so a reopened `db` gets a fresh cache automatically.
- **Test:** extend `tests/unit/core/sqlite-embeddings-content-hash.test.ts` (or `tests/unit/core/SQLiteStorage.test.ts`): (a) spy on `db.exec` via `vi.spyOn` after first `storeEmbedding`, assert zero further `exec` calls across 50 `getEmbedding`/`hasEmbedding` calls; (b) `clearCache()` then `storeEmbedding` works again (flag reset); (c) existing round-trip tests still pass.
- **Risk:** low — pure caching of an idempotent DDL; the flag resets with the connection. **Effort:** S.

Both run under `graphMutex` after `loadGraph()`, so `NameIndex` is populated. `hasEntity(name)` is O(1) on all three backends (`GraphStorage.ts:1696`, `SQLiteStorage.ts:1912`, `PostgreSQLStorage.ts:512`) and is on `IGraphStorage`. On a 100k-entity graph a single-entity create currently allocates a 100k-entry `Set`.
- **Change:** `EntityManager.ts:544-545` → `const entitiesToAdd = entities.filter(e => !this.storage.hasEntity(e.name));` (keep `graph.entities.length` for the limit check on `:546`). `RelationManager.ts:155` → delete the `Set`; `:160/:163` → `this.storage.hasEntity(relation.from)` / `.to`.
- **Test:** `tests/unit/core/EntityManager.test.ts` — add "createEntities with an existing name skips it (hasEntity path)" and "createEntities on a fresh storage before any loadGraph call still works" (ensures `ensureLoaded` precedes `hasEntity`; `loadGraph()` on `:542` already guarantees this). `tests/unit/core/RelationManager.test.ts` — existing dangling-relation tests cover the error path; add one asserting `hasEntity` is consulted (spy) rather than a full scan.
- **Risk:** low. **Effort:** S.

#### OPT-4 — BM25 recomputes IDF inside the per-document loop
- **Evidence:** `BM25Search.search` (`src/search/BM25Search.ts:248-268`): for every document and every query term, `const df = documentFrequency.get(term) || 0; const idf = … Math.log(...)`. IDF is a per-term corpus constant. Also `docEntry.docLength / avgDocLength` is per-doc but `k1 * (1 - b + b * …)` is recomputed per term.
- **Change:** before the loop: `const idfByTerm = new Map<string, number>(); for (const term of queryTerms) { const df = documentFrequency.get(term) || 0; idfByTerm.set(term, df > 0 ? Math.log((totalDocs - df + 0.5) / (df + 0.5) + 1) : 0); }` and drop query terms with `idf === 0` **only if** they also have `df === 0` (a term with df=0 contributes 0 for every doc). Inside the loop compute `const lenNorm = k1 * (1 - b + b * (docEntry.docLength / avgDocLength));` once per doc.
- **Test:** `tests/unit/search/BM25Search.test.ts` — add a determinism test: build a 50-entity fixture, capture `search()` scores before/after (Builder should capture the pre-change scores into the test as literals, or compare against a reference implementation written inline in the test) and assert exact equality (`toBeCloseTo(…, 12)`), including a query containing a term absent from the corpus.
- **Risk:** low. **Effort:** S.
